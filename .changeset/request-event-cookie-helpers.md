Request-event cookie helpers and the multi-`Set-Cookie` portability guarantee. `getCookie`/`setCookie`/`deleteCookie` ride the same ambient resolution as the response-head primitives (`getCookie(name)` resolves `getRequestEvent()`, `getCookie(event, name)` works against an explicit event): reads parse the request's `Cookie` header (request-only view — no read-your-writes merging), writes append `Set-Cookie` onto the event's response stub through a dependency-free serializer (`serializeCookie`/`parseCookieHeader`, percent-encoded round-trip, `Path=/` the only default) and are committed-aware — a write after the head went out throws in the dev build and reports + no-ops otherwise, never a silent drop. `deleteCookie` expires with an empty value and `Max-Age=0`, honoring `path`/`domain`. The server-function handler now folds the event's response stub onto every outgoing response as the head freezes (encoded results, envelopes, thrown redirects, raw passthroughs, no-JS form redirects) and marks it committed — previously `event.response` writes never reached the wire on that path. Every place response headers materialize or merge (`createSSRResponse`'s head derivation, the handler's envelope/raw forwarding, `respond`/`redirect` inits, the no-JS redirect build, frame-stream responses) now carries multiple `Set-Cookie` values entry-by-entry via `getSetCookie()` + append — never `get`/`set` or constructor-copy folding, which corrupts them on runtimes whose `Headers` iteration comma-joins — so multi-cookie responses survive identically across Node/undici, workerd and Deno. The flash-cookie codec's server half encodes/decodes through the same serializer/parser; the isomorphic regex matcher (`hasFlashCookie`/`matchFlashCookie`) is untouched, keeping the raw-payload contract and the client entry lean. Client entries stub the helpers like `getRequestEvent` (reads answer `undefined`, writes no-op). The stub gap-fill excludes the protocol-owned header family — the error/format/single-flight tags, `Location`, `X-Revalidate` — which must always reflect the response's own encoding, and skips `Content-Type`/`Content-Length` on bodiless responses (the no-JS redirect deliberately strips them); `Set-Cookie` appending is unaffected.
