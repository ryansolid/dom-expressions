Route `renderToStream`'s emission through semantic sink methods (`sink.data`, `sink.fragment`, `sink.reveal`, `sink.asset`, `sink.shell`) as the FrameSink extraction seams. The document sink remains the default and reproduces the existing inline `<script>`/`<template>`/`<link>` emission byte-for-byte; an experimental `options.sink` allows overriding individual sink methods.

Add the experimental frame producer on top of the seams: `createFrameSink` and `renderToFrameStream` (`src/frame-sink.js`, not in the public export surface) render through the same core and emit the transport-agnostic FrameChunk stream (`start`/`assets`/`html`/`data`/`fragment`/`reveal`/`complete`) instead of a document.

Add a serializer seam to `renderToStream` (`options.serializer` factory, defaulting to `createHydrationSerializer`) and a keyed streaming JSON-codec serializer pair in the shared substrate: `createJSONSerializer` (keyed `write(id, value)` over `toCrossJSONStream` with shared parse refs — cross-write referential dedupe, promise/stream patch nodes, flush/pending completion) and `createJSONDataTable` (keyed decode table over the shared-refs deserializer). Frame streams default to the codec: `data` chunks carry `{ key, node, initial }` — eval-free SerovalNode records — instead of executable hydration scripts.

Add `renderServerComponent` and the projection props proxy (`frame-sink.js`): rendering a `props => JSX` function emits projection marker ranges for prop reads (client-filled positions — the props a client passes never reach the server) and occurrence-keyed `slot` chunks for render-prop calls, with primitive args riding literally and other values codec-serialized as `{ $ref }` data records. The producing half of the "function returned from a server function is a server component" convention.

Add hydration attach to the client frame runtime: slot callbacks receive `ctx.existing` (the projection range's current interior — server-rendered client content on an adopted document-SSR boot); returning nodes replaces the interior (client render, no duplication), returning `undefined` claims the existing DOM in place with zero mutation (the hook a framework binding uses to hydrate over the range). Adopted frames sync slots at construction, so a document-SSR boot attaches without waiting for a chunk.

Complete the server-component convention over HTTP: `frameTransformResult` (a `transformResult` policy for `handleServerFunctionRequest`) turns a function result — or a `respond(fn, init)` envelope — into a frame-stream `Response` (`serverComponentResponse`): framed `JSON.stringify(FrameChunk)` over the shared server-function wire convention, tagged `X-Frame-Stream: <frame id>` (defaulting to the function id, so repeat calls target the same client boundary) and `X-Content-Raw` for handler pass-through. The client half (`frame-transport.js`) recognizes and pumps such responses into a frame host (`isFrameStreamResponse`/`applyFrameResponse`, with client-side boundary-id remapping via `as`). `createChunk`/`ChunkReader` are now exported from `server-functions/shared.js` so both transports share one framing implementation.

Add the frame insert brand: `insert` (client) recognizes values carrying the registered `$$FRAME` symbol and delegates mounting to the handler the value itself provides — `createFrameInsertable(options)` in `frame-client.js` creates such values (comment range + host-registered frame at the insertion point; teardown via `dispose()` on the value). client.js gains no frame imports, so apps that don't use frames pay zero bytes for them.

Add the experimental client frame runtime (`src/frame-client.js`, not in the public export surface): a resident keyed record store applying frame chunks into a DOM boundary — version-as-stale-guard, fragment placeholder ranges with reveal readiness buffering and fallback materialization, a projection-preserving server-owned morph, the slot model (direct-insert + render-function callbacks, iteration, threaded resolution), and a chunk-routing host with out-of-order buffering.
